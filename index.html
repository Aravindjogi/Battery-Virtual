Raw → Physical Conversion

Every signal in a CAN frame is stored as an integer raw value. The DBC (or our database) defines how to turn that into a meaningful engineering number.

Physical = (Raw × Scale) + Offset
ParameterMeaningExample
startBitBit position of the signal’s LSB (Intel) or MSB (Motorola)0, 16, 32…
lengthNumber of bits the signal uses8, 16, 1…
isSignedTwo’s-complement if true (negative currents, temps)true / false
scaleMultiplier applied to raw0.1, 0.001, 0.5
offsetAdded after scaling0, 2000 (year)
unitEngineering unit stringV, A, %, °C
min / maxValid physical range (for checks)0…1000 V

Why scale & offset?

  • Scale 0.1 → 16-bit raw 4106 becomes 410.6 V (0.1 V resolution).
  • Scale 0.001 → cell voltage 4102 → 4.102 V.
  • Offset 2000 + year raw 26 → 2026.
  • Signed current: raw −126 × 0.1 = −12.6 A (discharge).

How Bits Are Packed in a CAN Frame

A classic CAN frame carries up to 8 data bytes (64 bits). Signals are sliced out of this bit stream.

Intel vs Motorola (endianness)

Intel / Little-endian (@1)
  • LSB of the signal is at startBit.
  • Bits increase toward higher bit numbers.
  • Multi-byte: low byte first in the payload.
  • Common in many Western / automotive DBCs.
Motorola / Big-endian (@0)
  • MSB of the signal is at startBit.
  • Bit numbering often follows DBC “Motorola” layout.
  • Multi-byte: high byte first.
  • Very common in OEM vehicle networks.

Use the Byte Order buttons in the left panel to switch. This app’s bit map visualizer shows which bits belong to which signal after decode.

Bit numbering (0…63)

Byte0          Byte1          …  Byte7
[7 6 5 4 3 2 1 0][15 … 8] … [63 … 56]
 ↑ bit 0 is usually LSB of byte 0 (Intel view)

Signed values (two’s complement)

If the signal is signed and the MSB of the field is 1, the value is negative:

if (raw & (1 << (length-1))) raw = raw − (1 << length)

Example: 16-bit raw 0xFF82 → −126 → ×0.1 = −12.6 A.

Types of CAN Communication

Battery systems almost always use the Controller Area Network (CAN). Here is how the main variants work and how they relate to this analyzer.

TypeID lengthDataTypical use in BMS
CAN 2.0A
(Standard)		 11-bit ID
(0…0x7FF)		 0–8 bytes Most BMS ↔ VCU / charger traffic. This tool’s IDs (3E0, 541…) are 11-bit.
CAN 2.0B
(Extended)		 29-bit ID 0–8 bytes Some heavy vehicles, J1939. Same 8-byte payload; only ID is longer.
CAN FD 11 or 29-bit 0–64 bytes Newer EVs – more cells per frame, faster data phase. Same conversion math.
CANopen 11-bit + PDO/SDO 8 bytes Industrial / some ESS. NMT, TPDO (see ID 346, 3E6 in this DB).
J1939 29-bit PGN 8 bytes (+BAM) Commercial vehicles. Parameter groups instead of free IDs.

How a frame travels

  1. Arbitration – lower ID wins the bus (priority).
  2. Control – DLC (data length 0–8 for classic CAN).
  3. Data – the 0–8 bytes you paste into this tool.
  4. CRC + ACK – error check; receivers acknowledge.

This offline analyzer does not talk to real hardware. You feed frames (from a log, BUSMASTER, or demo) and it decodes them like a DBC-aware viewer.

Periodic vs event vs request/response

  • Periodic (cyclic) – BMS sends pack status every 10–100 ms (see cycle in database).
  • Event – fault flags change only when a fault appears.
  • Request/response – diagnostic UDS/ISO-TP (not modelled here; would be multi-frame).

Why many cell messages?

96 cells × 16 bits = 1536 bits ≈ 192 bytes. Classic CAN only carries 8 bytes per frame, so the BMS splits cells into groups of 4 (IDs 541, 542, … 558). This tool reassembles them into one cell table.

Worked Example — Pack Status (ID 3E0)

Sample data used by the Pack quick button:

CAN ID:  3E0
Data:    0A 10 82 FF A4 C0 00 64
         │  │  │  │  │  │  │  └─ reserved / power high
         │  │  │  │  │  │  └─── power low
         │  │  │  │  │  └────── SOH raw = 0xC0 = 192 → 192×0.5 = 96 %
         │  │  │  │  └───────── SOC raw = 0xA4 = 164 → 164×0.5 = 82 %
         │  │  │  └──────────── Current high (signed)
         │  │  └─────────────── Current low  → 0xFF82 = −126 → −12.6 A
         │  └────────────────── Voltage high
         └───────────────────── Voltage low  → 0x100A = 4106 → 410.6 V

Step-by-step (Intel / little-endian)

  1. Pack Voltage — startBit 0, length 16, unsigned, scale 0.1
    Bytes [0]=0x0A, [1]=0x10 → raw = 0x0A | (0x10<<8) = 4106
    Physical = 4106 × 0.1 + 0 = 410.6 V
  2. Pack Current — startBit 16, length 16, signed, scale 0.1
    Bytes [2]=0x82, [3]=0xFF → raw = 0xFF82 → signed −126
    Physical = −126 × 0.1 = −12.6 A (discharging)
  3. SOC — startBit 32, length 8, scale 0.5
    Byte [4]=0xA4 = 164 → 164 × 0.5 = 82 %
  4. SOH — startBit 40, length 8, scale 0.5
    Byte [5]=0xC0 = 192 → 192 × 0.5 = 96 %

Click Pack in the left panel, then Decode, and compare the Decoded Signals table and bit map with this explanation.

Try it yourself

Change byte 0–1 to E8 0F (0x0FE8 = 4072) → voltage should show 407.2 V. Or set current bytes to 64 00 (100) → +10.0 A (charging).

CANopen PDO Mapping

PDO (Process Data Object) carries real-time data with no protocol overhead. TPDO = this node transmits; RPDO = this node receives. Mapping decides which Object Dictionary (OD) variables fill the 0–8 data bytes and in what order.

TPDO vs RPDO

TermDirectionRole
TPDONode → busProducer (sends process data)
RPDOBus → nodeConsumer (receives process data)

One device’s TPDO is typically another device’s RPDO (same COB-ID).

Object Dictionary indices

RoleRPDOTPDO
Communication parameters0x1400 + n0x1800 + n
Mapping parameters0x1600 + n0x1A00 + n

n starts at 0 → PDO1, PDO2, …

Communication parameter (e.g. TPDO1 @ 0x1800)

SubNamePurpose
0Number of entriesUsually 2–5
1COB-ID11-bit ID + enable / RTR bits
2Transmission typeSync / async / event
3Inhibit timeMin gap between TPDOs (×100 µs)
5Event timerMax gap between TPDOs (ms)

COB-ID: bit 31 = 1 → PDO disabled; bit 30 = 1 → no RTR; bits 10–0 = CAN ID.

Mapping parameter (e.g. TPDO1 @ 0x1A00)

SubContent
0Number of mapped objects (0 = mapping off)
1…8One 32-bit mapping entry each
Bits 31…16 = OD index  |  Bits 15…8 = sub-index  |  Bits 7…0 = length (bits)

Length must be a multiple of 8 (8, 16, 24, 32…).

Decode a mapping entry

Index 0x6041 · Sub 0x00 · Length 16 bits (2 bytes)

Example mapping (drive-style TPDO1)

SubValueMeaning

1603F00100x603F:0 — Error code (16 bit)
2604100100x6041:0 — Status word (16 bit)
3606100080x6061:0 — Modes of operation display (8 bit)

Payload on the bus = those fields concatenated in order (little structure overhead).

Predefined connection set (Node-ID = N)

PDODefault COB-IDPDODefault COB-ID
TPDO10x180 + NRPDO10x200 + N
TPDO20x280 + NRPDO20x300 + N

Also: NMT 0x000, SYNC 0x080, EMCY 0x080+N, SDO 0x580+N / 0x600+N, Heartbeat 0x700+N.

Transmission types (comm sub-index 2)

ValueBehaviour
0Acyclic synchronous — on SYNC if data changed
1–240Cyclic synchronous — every n-th SYNC
254 / 255Asynchronous / event-driven

Safe procedure to change mapping

  1. Put node in Pre-Operational (NMT).
  2. Disable PDO: set bit 31 of COB-ID.
  3. Set mapping sub-index 0 = 0 (clear mapping).
  4. Write new mapping entries (sub 1, 2, …).
  5. Set sub-index 0 to the new object count.
  6. Enable PDO (clear bit 31 of COB-ID).
  7. Switch to Operational.

Link to this analyzer

Your database already includes CANopen-style messages such as 346 (TPDO6) and 3E6 (NMT / heartbeat). PDO mapping is the CANopen name for “which signals live in this 8-byte frame” — the same idea as the signal list in database.js, without the OD index packing.

Battery Thermal Management (BTMS)

Temperature is one of the strongest drivers of safety, life, and performance. A Battery Thermal Management System keeps every cell inside a safe window (typically ~15–35 °C for Li-ion operation; tighter for fast charge).

Why temperature matters

ConditionEffectTypical BMS action
Too hot (e.g. >45–60 °C)Accelerated aging, risk of thermal runawayLimit/derate current, stop charge, request cooling
Too cold (e.g. <0–10 °C)High resistance, lithium plating on chargePreheat, block/limit charge, limit discharge
Large ΔT between cellsUneven aging, capacity mismatchBalance + cooling strategy; flag imbalance

Cooling / heating methods

TypeHow it worksNotes
Air coolingFans force air across modulesSimple, lower cost; limited for high power
Liquid coolingCoolant plates / channels under modulesCommon in EVs; excellent uniformity
Refrigerant / directA/C loop or immersion conceptsHigh performance fast-charge packs
HeatingPTC heaters, heat pump, waste heatCold climate charge enable
Phase-change materialsAbsorb heat at phase transitionPassive buffer; often hybrid with liquid

What the BMS measures & reports on CAN

  • Module / cell temperatures (this tool: IDs 3F0, 3F1)
  • Max / min temperature and which sensor
  • Over-temperature / under-temperature fault flags (ID 3E5)
  • Derating limits: max charge/discharge current vs temperature

Heat generation is dominated by I²R losses and reaction heat during charge/discharge. Approximate electrical heat: Heat ≈ I² × R × t (see Battery Calculator → Heat Loss).

Control loop (simplified)

Sensors (T, V, I) → BMS estimates heat & limits
        → requests cooling/heating from vehicle/thermal controller
        → updates max charge/discharge on CAN (e.g. 3E1)
        → raises OT/UT faults if limits exceeded

How BMS Protocols Work

A Battery Management System is both a safety controller and a communication node. Protocols define how pack data, limits, and faults are shared with the vehicle control unit (VCU), charger, and diagnostics tools.

Protocol layers in practice

LayerRoleExamples
Physical / data linkBits on the wireCAN 2.0A/B, CAN FD
TransportMulti-frame if neededISO-TP (diagnostics)
Application mapWhat each ID/byte meansDBC, CANopen OD, proprietary map
Device profileStandard object meaningsCiA 301/402, J1939 PGNs, UDS services

Common BMS communication styles

StyleHow it worksIn this analyzer
Proprietary CAN + DBC Fixed 11-bit IDs; signals defined by startBit, length, scale, offset Primary mode — database.js / Import DBC
CANopen PDO/SDO Process data via TPDO/RPDO mapping; parameters via SDO; NMT state machine Learn tab 6; sample IDs 346, 3E6
J1939 29-bit ID with PGN + source address; parameter groups Same decode math once PGN payload is defined
UDS / OBD diagnostics Request/response (ISO-TP); read DTCs, freeze frames Not simulated; offline frame decode still applies to logged data

Typical BMS ↔ vehicle data flow

Cell V/T sensors → AFE / BMS MCU
        → pack algorithms (SOC, SOH, limits, faults)
        → CAN TX: status, cells, temps, faults, limits
        → VCU / charger / logger / this Analyzer
        ← CAN RX: contactor commands, charge enable, thermal requests

Core BMS functions tied to protocol traffic

  • Monitoring — voltage, current, temperature (cyclic PDOs / status frames)
  • Protection — OV, UV, OT, UT, over-current, isolation (fault frames)
  • Estimation — SOC, SOH, remaining capacity (status frames)
  • Balancing — which cells discharge/transfer (balance status)
  • Contactor & precharge — HV safety interlock feedback
  • Thermal interface — request cooling/heating; report sensor temps

Decoding always reduces to: frame ID + payload bytes → signals via scale/offset (and for CANopen, OD mapping that builds those payloads).

CC / CV Charging — How Real Chargers Work

Almost all lithium packs (and Chroma-style cyclers) use Constant Current / Constant Voltage. The simulator and Recipe Editor follow the same stages.

1. Constant Current (CC)

  • Charger forces a fixed current (e.g. 0.5C → 25 A on a 50 Ah pack).
  • Pack voltage rises slowly as SOC increases (OCV + small I×R).
  • Example 15S LFP @ 30% SOC ≈ 48.2 V → then 49 V, 49.3 V, … toward charge voltage.
  • CC ends when pack voltage reaches the configured charge voltage (e.g. 53.5 V).

2. Constant Voltage (CV)

  • Charger holds pack at charge voltage (e.g. 53.5 V).
  • Current tapers down as the pack accepts less current.
  • Charging stops when current falls to CV cutoff current (e.g. 0.05C → 2.5 A).
  • That event is End of Charge (EOC) — charge MOSFET opens.

3. Modes in this app

CV onlyHold voltage, taper currentRecipe mode = CV

  • Discharge step: CC only — set Current and End SOC (or time).
  • Blank currents use Pack Builder limits. Optional step fields: set Time for duration; End SOC for capacity limits.
  • Blank CV Icut uses Pack Builder CV cutoff current.

Pre-charge Circuit — Why and How

When a high-voltage pack connects to a capacitive DC link (inverter, charger input), the instantaneous current can be thousands of amps if closed hard. A pre-charge path limits inrush, then the main contactor closes.

Pack +→ Pre-charge relay + R→ DC-link C→ Load / Inverter
Pack +→ Main contactor→ DC-link C (closes after V_link ≈ 90–95% of V_pack)

Live path animation

IDLE Yellow path = pre-charge (limited I). Green = main contactor after V_link high. Red flash = hard close inrush.

RC charging law

V(t) = V_bus × (1 − e−t/(R·C))

MOSFET & Contactor in a BMS

Low/mid voltage packs often switch charge and discharge with power MOSFETs. High-voltage systems use contactors (electromechanical) plus a pre-charge path.

Charge / Discharge MOSFET pair

  • Charge MOSFET — blocks discharge when OFF (body diode orientation matters).
  • Discharge MOSFET — blocks charge when OFF.
  • Back-to-back FETs or ideal-diode controllers are used so current can be blocked both ways.
V_drop = I × R_ds(on)   ·   P_loss = I² × R_ds(on)

Parallel MOSFETs: R_eq ≈ R_ds / N (share current; match packages and layout).

Contactor

  • Coil energised → main contacts close (high continuous current).
  • Needs pre-charge; contacts weld risk if closed into a large capacitor bank.
  • Auxiliary contacts feedback to BMS for weld/stuck detection.

BMS MOSFET count

Battery Maker lets you choose how many charge/discharge FETs in parallel for current capability and thermal margin. More FETs → lower R_ds effective → less heat, higher cost and gate-drive complexity.

MOSFET Leakage & Residual Voltage

When a MOSFET is OFF, a small leakage current (I_DSS / I_off) still flows. On a floating output or slow-bleed load, this can create a measurable residual voltage.

I_leak ≈ datasheet I_DSS @ V_DS, T_j   ·   V_residual ≈ I_leak × R_load

Why it matters in BMS

  • Load appears “slightly alive” after discharge FET opens.
  • Isolation measurement and bleed resistors are sized with leakage in mind.
  • Leakage rises strongly with temperature — design margins at hot condition.

Mitigation

  • Bleed / discharge resistor across load or DC link.
  • Two FETs in series for higher off-state voltage rating.
  • Contactor air gap (true galvanic isolation when open).

Calculator: Leakage I ≈ V / R_off (simple model for education).

Pyro Fuse Trigger Model

A pyrotechnic fuse (pyro fuse) opens the HV path by an explosive charge when the BMS or crash ECU commands it, or when current exceeds a design threshold.

  1. Armed — device intact, continuous current path closed.
  2. Trigger — gate signal or overcurrent condition.
  3. Delay — typically a few milliseconds for ignition.
  4. Fired / open — permanent open; pack isolated. Not resettable.
Fire if |I| ≥ I_trigger for t ≥ t_delay   (or digital crash request)

In Battery Maker set type to Pyro fuse, set trigger current and delay, then use Test pyro trigger or drive a short in the simulator.

How CAN H and CAN L Carry Data

An ECU's digital bits (0s and 1s) are converted by the CAN transceiver into two opposite electrical signals — CAN H and CAN L — sent together as a twisted differential pair. The receiving transceiver reads the voltage difference between them, not either wire alone, which is what makes CAN so resistant to electrical noise.

Live transmission animation

IDLE Enter a bit stream (0/1) and press Transmit to watch the ECU's digital bits become CAN H (red) / CAN L (green) differential voltage.

Voltage levels (typical — high-speed CAN)

Bus stateCAN HCAN LDifferential
Recessive (1) — no data~2.5 V~2.5 V~0 V
Dominant (0) — data~3.5 V~1.5 V~2 V
Key point
  • Bit 1 (Recessive): CAN H and CAN L sit at the same ~2.5 V level.
  • Bit 0 (Dominant): CAN H rises to ~3.5 V while CAN L drops to ~1.5 V.
  • The receiver decodes the bit from CAN H − CAN L, not the absolute voltage on either wire.
  • This differential method is what makes CAN reliable in noisy automotive/EV environments.

Quick summary

  • Bit 0 (Dominant) → CAN H high (~3.5 V), CAN L low (~1.5 V)
  • Bit 1 (Recessive) → CAN H ≈ CAN L (~2.5 V each)
  • Data is determined by the difference between CAN H and CAN L
  • Any dominant bit on the bus overrides recessive bits — this is how CAN arbitration works

CAN Arbitration — Who Gets to Talk?

CAN has no master and no fixed time slots. If two or more ECUs start transmitting at exactly the same moment, they settle it bit-by-bit on the wire itself — with zero data loss and zero delay for the winner. This is called non-destructive bitwise arbitration.

  1. All contending nodes transmit their arbitration ID bits simultaneously, MSB first.
  2. Every node also reads the bus while it transmits.
  3. If a node sends recessive (1) but reads back dominant (0) — because another node sent 0 — it knows it lost, and immediately stops transmitting and retries later.
  4. The node with the numerically lowest ID (most leading zeros) always wins — it's the highest priority message, and it wins with no retransmission needed.

Live arbitration animation

IDLE Enter three binary IDs (0/1, same length = same priority field) and press Arbitrate to watch them contend bit-by-bit for the bus.
Node sendsBus reads backResult
Recessive (1)Recessive (1)Still contending
Dominant (0)Dominant (0)Still contending
Recessive (1)Dominant (0)Lost arbitration — stop transmitting
Key point
  • Lower numeric CAN ID = higher priority. More leading zero bits win first.
  • The losing node's frame is not corrupted or dropped — it simply waits and retries as soon as the bus is free.
  • This is why safety-critical messages (e.g. pack fault, over-current) are assigned low CAN IDs — they always win the bus.
  • Arbitration happens in the same bit window used for the CAN H/CAN L voltage race you saw in the previous tab.

Quick summary

  • Multiple nodes can start transmitting at once — no collision, no corrupted data
  • First node to send a 1 while the bus is 0 loses and backs off instantly
  • Lowest ID = highest priority = wins every time, deterministically
  • Design tip: keep fault/alarm/BMS-critical IDs numerically low in your CAN ID Browser
